Central Claim

Can a single developer build a working interpreted programming language from scratch and use it — without external libraries — to implement non-trivial algorithms like the Fast Fourier Transform and the Number Theoretic Transform? This project answers yes.

Execution Pipeline
01 Lexer Raw source text → named tokens. Whitespace and comments discarded.
02 Parser Token stream → Abstract Syntax Tree via recursive descent with precedence climbing.
03 AST Tree of typed nodes — expressions, statements, operators, closures.
04 Interpreter Tree-walking evaluator with a scoped environment stack. Closures captured at definition time.
Language Features
  • First-class functions — lambdas, named functions, closures, default parameters
  • Full operator set — arithmetic, bitwise, boolean, ternary, compound assignment
  • Mutable lists — indexed read/write, slice access (a[0::2])
  • Control flow — if/elif/else, while, for-in loops
  • User-defined types — mutable struct and immutable record
  • Recursion — full support, used directly in FFT decomposition
  • Parse-time validation — default parameter ordering checked before execution

Arithmetic Approach

Standard FFT computes roots of unity as floating-point complex numbers — which introduces rounding error. This project avoids floats entirely using two exact alternatives:

Standard FFT   e2πi/n float · inexact
NTT   g(p−1)/n mod p integer · exact
Gaussian FFT   ℤ[i] mod p integer · exact

NTT uses prime p = 998244353 with primitive root g = 3. The Gaussian FFT works in pairs of integers [re, im] where i² ≡ −1 (mod p).

Verified Result

Both FFT and NTT variants produce identical output, cross-validated against a naive O(n²) baseline:

a = [1, 2, 3];
b = [4, 5, 6];
pprint(polymul_ntt(a, b));
OUTPUT [4, 13, 28, 27, 18]

Corresponds to the polynomial product:
(1+2x+3x²)(4+5x+6x²)
